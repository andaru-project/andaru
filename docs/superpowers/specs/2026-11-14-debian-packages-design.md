# Debian packages and the signed APT repository

## Status and intent

Slice 1 of [issue #13](https://github.com/andaru-project/andaru/issues/13) (install, upgrade, backup and reset). Today an operator installs Andaru by copying a binary and some twenty files from `packaging/` by hand, as the guide's sections list. This slice turns that into `apt install andaru` from a signed repository, so a clean Debian 13 host reaches the point where `andaru ctl takeover` can run with one verified bootstrap step and two apt commands. Later slices of #13 build on it: upgrades with automatic rollback, backup and restore, factory reset, Debian security updates.

Decisions already recorded on #13 that this slice implements:
- **A real package** shipping Andaru's binary, with dependencies; not a metapackage.
- **A signed APT repository over HTTPS**, trusted only for itself through deb822 `Signed-By:`, never through global APT trust; signature checks are never bypassed.
- **Bootstrap:** a small `.deb` verified against a separately published checksum, then ordinary apt installation. No curl-pipe-shell.
- **Key hierarchy:** an offline primary key; the repository is signed by a subkey that expires after 5 years; new keys reach installed systems through the `andaru-archive-keyring` package; `Valid-Until` in `Release` against replayed repositories.
- **`nftables.service` is masked:** a restart of Debian's unit flushes the whole ruleset, so a package upgrade restarting it would wipe Andaru's filter.
- **Uninstalling is not supported;** upgrades are.

Owner decisions, 2026-11-14:
- **Hosting:** GitHub Pages on `andaru-project/apt`, served at `https://apt.andaru.io/` (Cloudflare DNS, DNS-only `CNAME` to `andaru-project.github.io`; HTTPS enforced). Done.
- **The archive key:** generated by the owner on his own machine. Primary `7CD6177785416B306999DEF2B5E7EDE2133D18DF` (Ed25519, certify only, expires 2036-11-11), kept offline. Signing subkey `67BF6A43DD97A19C2AEDE7294FA659D5E10049DD` (Ed25519, sign, expires 2031-11-13), held unencrypted as the `APT_SIGNING_KEY` Actions secret of `andaru-project/apt`, and nowhere else. Done.
- **Building:** a `debian/` directory built with debhelper (Approach A); the repository indexed with `apt-ftparchive`.

Not implemented behaviour. Contracts remain provisional until Andaru 1.0.

### Probe behind it

Debian 13 container (systemd 257.13), 2026-11-14:
- Debian's AppArmor profiles include `local/usr.sbin.<daemon>`, and those files exist but **no package owns them**: each daemon's `postinst` creates them empty for the administrator. A package shipping them would collide with them.
- `iproute2` keeps its tables in `/usr/share/iproute2/` (no `/etc/iproute2`).
- `/usr/share/kea/scripts` is owned by no package; Kea's `run_script` hook names whatever path it is given.
- Debian 13's Go is 1.24; Andaru needs 1.27.

## The packages

One source package, `andaru`, in `debian/` at the repository root, built by `dpkg-buildpackage` with debhelper (compat 13) in a Debian 13 container, natively on amd64 and arm64.

### `andaru` (Architecture: any)

| File | Installed at |
| --- | --- |
| the binary | `/usr/bin/andaru` |
| `andaru-engine.service`, `andaru-network-boot.service`, `andaru-leases.{path,service}`, `andaru-prefixes.{path,service,timer}` | `/usr/lib/systemd/system/` |
| the Kea drop-ins | `/usr/lib/systemd/system/kea-dhcp{4,6}-server.service.d/andaru.conf` |
| `ManageForeignRoutes=no` | `/usr/lib/systemd/networkd.conf.d/andaru.conf` |
| the `andaru` route protocol (77) | `/usr/share/iproute2/rt_protos.d/andaru.conf` |
| the tmpfiles entry | `/usr/lib/tmpfiles.d/andaru.conf` |
| the lease event hook | `/usr/share/kea/scripts/andaru-lease-event` |
| Unbound's include | `/etc/unbound/unbound.conf.d/andaru.conf` (a conffile, as Unbound reads only `/etc`) |
| the AppArmor rules | `/etc/apparmor.d/andaru/{kea-dhcp4,kea-dhcp6,unbound}` (conffiles) |

Vendor locations (`/usr/lib`, `/usr/share`) wherever the reading program has one, so an administrator's files in `/etc` still win.

**Relations:**
- `Depends:` `systemd (>= 257)`, `nftables`, `iproute2`, `${misc:Depends}` (the binary is static).
- `Recommends:` `kea-dhcp4-server`, `kea-dhcp6-server`, `unbound`, `openssh-server` (#14: setup allows SSH from the management segment), `apparmor`.
- `systemd-resolved` is not a dependency: on a cloud image it is already in charge, and on an ifupdown host the takeover's existing check (`RESOLVED_NOT_IN_CHARGE`) tells the operator to install it and reboot, because installing it there changes the host's resolver at once.

The binary is built with the Go toolchain from `go.mod` (`actions/setup-go`), not Debian's 1.24, with `CGO_ENABLED=0` as the lab builds are; `debian/rules` overrides `dh_auto_build`/`dh_auto_install` to `go build -trimpath` and install it.

### Maintainer scripts

`postinst configure`:
1. **Mask `nftables.service`** (`deb-systemd-helper` is not used for a unit of another package: plain `systemctl mask nftables.service`). Masking never stops a running unit, and a host Andaru has not taken over keeps whatever ruleset it had; the takeover already loads Andaru's table. If `nftables.service` is active at install, it stays active until the next boot, which the takeover precedes; the postinst prints that.
2. **AppArmor:** for each of `usr.sbin.kea-dhcp4`, `usr.sbin.kea-dhcp6`, `usr.sbin.unbound` whose profile exists, add the line `include if exists <andaru/<daemon>>` (AppArmor 4, as Debian 13 ships) to `/etc/apparmor.d/local/usr.sbin.<daemon>` if it is missing (creating the file if needed, as the daemon's own postinst would), then `apparmor_parser -r` that profile. One marked line in the administrator's file, never a replaced file. When a daemon is installed after Andaru, a `dpkg` file trigger on `/etc/apparmor.d/usr.sbin.kea-dhcp4` (and the others) reruns the same step.
3. `systemd-tmpfiles --create andaru.conf`.
4. Units, through `dh_installsystemd`: enable `andaru-engine.service`, `andaru-network-boot.service`, `andaru-leases.path`, `andaru-prefixes.path`, `andaru-prefixes.timer`; start the engine and the path and timer units; never start the oneshots (`andaru-network-boot`, `andaru-leases.service`, `andaru-prefixes.service`) at install or upgrade. On upgrade the engine is restarted (it serves only the local socket; restarting it touches no network).
5. **Never** `networkctl reload`, restart networkd, or touch an interface: installing a package must not disturb the link the operator is on. `ManageForeignRoutes=no` therefore takes effect at the next networkd restart, which the first boot after the takeover provides.

`prerm` and `postrm`: units are stopped on removal by `dh_installsystemd`'s defaults, except `andaru-network-boot` (nothing to stop). `postrm purge` removes nothing under `/var/lib/andaru`: that state is the host's network configuration, and uninstalling is not a supported path. It leaves `nftables.service` masked; the purge removes the `include` lines it added (they would be harmless, being `if exists`, but they are not the administrator's).

### `andaru-archive-keyring` (Architecture: all)

- `/usr/share/keyrings/andaru-archive-keyring.gpg`: the public key (primary and signing subkey), binary form, built from `debian/keyring/andaru-archive-key.asc`, the armoured key the owner exported (committed with this design).
- `/etc/apt/sources.list.d/andaru.sources` (a conffile):
  ```
  Types: deb
  URIs: https://apt.andaru.io/
  Suites: trixie
  Components: main
  Signed-By: /usr/share/keyrings/andaru-archive-keyring.gpg
  ```
- Its version is independent of Andaru's (`2026.11.14`), so a key rotation ships alone. It is **built once**, by its own tag `keyring-2026.11.14`, and never rebuilt for that version: one file, one checksum, which the guide then records. Andaru's release tags build only `andaru`.

## The repository

`https://apt.andaru.io/`, the `main` branch of `andaru-project/apt`:

```
andaru-archive-key.asc                      the public key, armoured
andaru-archive-keyring_<version>_all.deb    the bootstrap package, also in pool/
SHA256SUMS                                  of the bootstrap packages
dists/trixie/InRelease, Release, Release.gpg
dists/trixie/main/binary-{amd64,arm64}/Packages, Packages.gz
pool/main/a/andaru/…, pool/main/a/andaru-archive-keyring/…
```

- `Release`: `Origin: Andaru`, `Label: Andaru`, `Suite: trixie`, `Codename: trixie`, `Components: main`, `Architectures: amd64 arm64`, `Date`, and `Valid-Until` 14 days later. `Acquire-By-Hash` is not used.
- **Retention:** the newest five versions of `andaru` stay in `pool/` (slice 2's rollback needs the previous one); older ones remain on their GitHub releases. A release is about 25 MB for both architectures, and GitHub Pages sites are limited to 1 GB.
- **Test releases** are GitHub prereleases with versions like `0.4.0~rc1` (which sort before `0.4.0`), published to a separate suite, `trixie-test`, with its own `dists/trixie-test/` and the same pool and key. Hosts see them only by adding that suite; the lab does. Prereleases never enter `trixie`.
- **Publishing** is a workflow in `andaru-project/apt`, the only place the signing key exists. It runs on `workflow_dispatch` (a tag) and daily on a schedule. It downloads the `.deb`s and `SHA256SUMS` of every Andaru release from `andaru-project/andaru`'s public GitHub releases that the pool lacks, checks them against the release's `SHA256SUMS`, regenerates the indexes with `apt-ftparchive`, signs `InRelease` and `Release.gpg` with the subkey, and commits. The daily run re-signs even without a new release, so `Valid-Until` never lapses on a maintained repository. Andaru's repository holds no credential for the APT repository.
- **Versions:** the tag `v<version>` gives the Debian version `<version>-1`; the first release is `v0.4.0`, matching the API document's `0.4.0-dev`. `debian/changelog` gets its entry from the tag in the release workflow.
- **Releasing** is a workflow in `andaru-project/andaru`, on a pushed tag `v<version>`: it builds both architectures' `andaru` and the keyring package, runs `lintian`, and creates the GitHub release with the `.deb`s and `SHA256SUMS`. It holds no credential to start the publishing workflow; the next daily run publishes the release, or the owner starts it at once with `gh workflow run publish -R andaru-project/apt -f tag=v<version>`.

## Hosts installed by hand

Hosts set up by copying `packaging/` files (developer machines; the lab VMs are reset to pre-Andaru snapshots for each run) do not convert in place: copies in `/etc/systemd/system/`, `/etc/systemd/networkd.conf.d/`, `/etc/iproute2/rt_protos.d/` and full rule copies in `/etc/apparmor.d/local/` would override or duplicate the package's files. The guide lists them to delete before `apt install andaru`. The "From source" section keeps hand installation for development, copying to the package's own paths.

## The bootstrap

Documented in the guide and the README, with the checksum shown in two independently published places (the guide on `github.com` and the release notes):

```sh
curl -fsSLO https://apt.andaru.io/andaru-archive-keyring_2026.11.14_all.deb
echo '<sha256>  andaru-archive-keyring_2026.11.14_all.deb' | sha256sum -c
sudo apt install ./andaru-archive-keyring_2026.11.14_all.deb
sudo apt update && sudo apt install andaru
```

The guide also prints the primary key's fingerprint, for those who verify `andaru-archive-key.asc` by hand.

## CI

- Every pull request builds both architectures' packages and runs `lintian` (no errors; warnings listed), then installs `andaru` with its recommends in a Debian 13 container booted with systemd and checks: the files above, `nftables.service` masked, Andaru's units enabled, the engine answering `andaru ctl links`, the AppArmor `include` line present (the container's apparmor parse is skipped where the kernel has none).
- The existing tests and gates are unchanged.

## Acceptance

- **Automated:** the CI checks above; a test of the AppArmor include step against a scratch root (adds once, keeps the administrator's own lines, creates a missing file); the publishing workflow run once by hand on a test tag, its repository verified with `apt update` against the keyring in a Debian 13 container, and `Valid-Until` and the signer's subkey checked.
- **Lab:** on a fresh Debian 13 genericcloud VM and a minimal (ifupdown) VM: the bootstrap and `apt install andaru` from `apt.andaru.io`, without touching the operator's link; `andaru ctl takeover --accept-detected`, apply, confirm; reboot; then an upgrade to a second test release with `apt upgrade`, the engine restarted and the network untouched; `nftables.service` masked throughout.
- **The guide:** "Installing" leads with the bootstrap; the hand-copy lists move to a "From source" section for developers.

## Approaches

- **A, chosen: debhelper.** Debian's helpers write unit enablement, conffile handling and triggers; `lintian` checks the result; it fits the masking and slice 2's rollback.
- **B: nfpm.** One YAML file, no Debian tooling, but hand-written maintainer scripts.
- **C: `dpkg-deb` from a script.** The least tooling and the most hand-written.

The repository: `apt-ftparchive` (one distribution, one component, every version kept) over `reprepro` or `aptly`, which suit many distributions and add a database.
